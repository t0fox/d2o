# Обрывы сети при YouTube и корпоративном VPN

## Полевой снимок

Источник — `d2k-diagnostics (8).json`, релиз `d2o-20261113-1821-cd88413`.
Исходники сверены с `main` на `7a5fab97a1a7`. Разница между ревизиями
в отслеживаемых путях контроллера, датапата, runtime и установленных
правил отсутствует.

В снимке 120 записей с 18:08:19 до 21:12:41 МСК (UTC+3). Самый длинный разрыв
между записями — 601 с. Время обрыва Windows/VPN в выгрузке не указано.

| --- | --- |
| Свободный CPU по сглаженной оценке AIMD | 64–98% в снимках. В отдельных переходах AIMD указан CPU |
| Доступная память | 324 496–341 732 КиБ из 496 716 КиБ |
| Conntrack | 88–1 466 из 31 232 записей (до 4,7%) |
| Одновременно активные измерения | До 6, ожидающие — до 1 |

Длительность поиска включает ожидание сети и последовательные стадии.
Выгрузка не связывает эти измерения с обрывом и не позволяет оценить короткие
пики CPU отдельного процесса, очередь ядра, вердикты, WAN и ошибки DNS
в момент отказа. Данные по доступной RAM и conntrack относятся к попавшим
в выгрузку моментам на роутере с примерно 485 МиБ RAM.

## Как трафик и измерения расходуют ресурсы

- `files/S99d2k` ведёт в NFQUEUE первые 8 пакетов каждого направления TCP и
  UDP по всему диапазону портов. После этого окна идут поздние TCP FIN/RST и
  трафик открытого HTTP на порту 80. Таким образом, старт и реконнект
  VPN могут пройти через ту же очередь, что и новый поток видео.
- `d2kd` обслуживает NFQUEUE в одном цикле со сборкой приветствий, выдачей
  отложенных вердиктов, запросами ctnetlink для наблюдаемых потоков и записью
  журнала. Отдельные флаги обхода очереди без слушателя и fail-open при
  переполнении действуют в ядре. Они не сокращают время ожидания пакета,
  уже принятого в очередь и ещё ждущего вердикт.
- `d2kc` запускает классификацию в рабочих потоках. Обычные активные
  измерения с `MEASURE_MARK` обходят эту NFQUEUE, а проверки кандидата с
  `PROBE_MARK` проходят через неё. CPU, исходящий канал и conntrack общие
  с пользовательским трафиком. AIMD снижает допуск новых замеров при
  нехватке ресурсов, уже запущенные замеры продолжаются. Одинаковые
  подозрения объединяются по цели/семейству адреса/транспорту, а новый
  снимок формы может потребовать повторной классификации. Синхронный
  `pthread_join` на части переходов может задержать контроллер. Вклад
  этих путей в полевой отказ пока не измерен.
- Обычный DNS на 53 проходит вне очереди. Зашифрованные DoH/DoT/DoQ могут
  проходить через неё. Проверка DNS-ответа идёт в отдельном рабочем потоке,
  а периодический запрос конфигурации Keenetic через `ndmc` выполняется в
  цикле контроллера, с лимитом ожидания 250 мс перед остановкой дочернего
  процесса. Сбой DNS или проверки Windows может дать восклицательный знак
  при доступном IP-соединении.

## Воспроизведённый дефект

При одном `POLLERR` прежний цикл пропускал `recv`, поэтому асинхронная
ошибка сокета оставалась активной и `poll` немедленно будил цикл снова.
Linux netlink сообщает об overruns через `sk_err = ENOBUFS`. Считывание
этого состояния необходимо и без доступного пакета.

Регрессия `make -C datapath test-nfq-poll-event` создаёт на Linux состояние
`POLLERR` без `POLLIN` на локальном UDP-сокете. На прежнем условии тест
падает («poll error without POLLIN skipped by the event loop»). После
правки ошибка вычитывается, `poll` возвращается к ожиданию; чтение пустого
сокета неблокирующее. Это воспроизведение пути ошибки, а не воспроизведение
полевого VPN-обрыва.

## Экспорт диагностики

Включить общую диагностику и оставить её включённой до воспроизведения.
Экспорт `network_history` хранит 240 срезов с шагом около 2 с (около восьми
минут). После сбоя записать время с секундами, пояс, факт потери уже
открытого туннеля и возможность нового подключения. После следующего
обновления отчёта, максимум примерно минута при доступном роутере, выгрузить
JSON. История в памяти переживает перезапуски `d2kd` и `d2kc`; при
перезапуске сборщика сохраняется только последний записанный отчёт до
его замены, после перезагрузки роутера tmpfs очищается.

У каждого компактного массива в JSON есть список имён полей. Для анализа
сравнивать изменения накопительных счётчиков в пределах одного PID и
`start_ticks` и с учётом переполнения 32-битных счётчиков ядра. Пустой
или устаревший источник передаётся как `null`; время `mono_ms` источника
отличает повторы среза. Windows-время сравнивается с `at` (Unix-секунды),
длительности рассчитываются по монотонным часам.

- CPU выражен в процентах одного ядра за интервал, поэтому многопоточный
  процесс может превышать 100%. Добавлены счётчики запущенных и повторных
  классификаций, завершённых единиц зондов, истечения фаз/очереди, TCP dial
  deadlines, ошибок конфигурации и bootstrap/health-проверки DNS.
  Пользовательские запросы и ответы DNS штатного резолвера не захватываются.
- NFQUEUE берётся по номеру очереди и port ID сокета. Различаются текущий
  backlog, два счётчика потерь очереди, потери сокета netlink и уведомления
  `ENOBUFS`. Fail-open может пропустить трафик при переполнении без роста
  `kernel_drops`. Задержка от чтения до отправки вердикта измеряется
  монотонно. Метрика от времени пакета ядра до отправки требует
  `NFQA_TIMESTAMP`; она может включать время до входа в очередь. Размер
  таблицы временных измерений ограничен, совпадение проверяется по ID пакета.
- Conntrack берётся из sysctl и доступных счётчиков procfs; WAN — по
  видимым маршрутам по умолчанию IPv4/IPv6 и состоянию выбранного интерфейса
  в sysfs. Это состояние маршрута/линка, а не активная проверка интернета,
  нескольких таблиц policy routing или конкретного VPN-шлюза.
- Для TCP учитывается ранее наблюдавшаяся полезная нагрузка в обе стороны,
  для UDP — ранее наблюдавшиеся датаграммы в обе стороны. В отчёт попадают
  только агрегаты TCP/UDP и действия hold/plan/повторной посылки/HTTP,
  без адресов, имён, портов и содержимого пакетов в этой секции. Одно
  взаимодействие может дать несколько действий. Без попадания в NFQUEUE
  или после вытеснения записи обмен не виден. Это признаки вмешательства,
  а не распознавание VPN. Обычная выгрузка D2O по-прежнему содержит
  диагностические имена и адреса целей поиска.
- Кольцо на x86-64 занимает 165 256 байт в `d2kdiag` при включённой общей
  диагностике, статический предел 176 КиБ. Отдельное маленькое
  хранилище времени вердиктов в датапате — около 3 КиБ. Сборщик сохраняет
  прежние nice, RLIMIT_AS и минутную периодичность записи полного отчёта.

## Нагрузочная проверка

`sh scripts/lab-network-stress.sh` запускает изолированный стенд на Linux
с Docker и доступным модулем `nfnetlink_queue`. Две отдельные сетевые
области имитируют LAN и сервер. Сравниваются NAT с базовой нагрузкой и
NAT с production nft-правилами, `d2kd`, `d2kc` и сборщиком. Клиент
одновременно запрашивает подлинные HTTP/3 и HTTPS медиасегменты и гоняет
постоянные TCP/UDP-туннели с проверкой каждого сообщения. Отдельный локальный
TLS-адрес пропускает SYN и глушит ClientHello для запуска реальных
измерений. Стенд требует доказательства активности NFQUEUE и фонового
поиска и сохраняет отчёт, ошибки и RTT. `D2O_STRESS_SECONDS=300` увеличивает
обе фазы до пяти минут.

В доступном окружении подтверждены C-тесты NFQUEUE, сессий, UDP-удержания,
сборщика, диагностики памяти и жизненного цикла 1 500 имитированных
измерений. Сборки `d2kd`, `d2kc`, `d2kdiag` для ARM64 и MIPS32 LE
со статической musl прошли. За 30 с на loopback, без NFQUEUE и контроллера,
клиент получил 3 749 HTTPS и 709 HTTP/3 сегментов, а оба туннеля — по
598 ответов без таймаутов. p95 составил 4,932 мс для TCP и 4,663 мс для UDP.
Стенд с реальной NFQUEUE требует Docker и сетевых прав, отсутствующих в
этой среде. Тесты с AF_UNIX и `getifaddrs` встречают ограничения среды
также на исходной ревизии. Физические Keenetic/OpenWrt и пиковое потребление
памяти на 128 МиБ остаются непроверенными.

## Что требуется отличить следующим полевым снимком

1. Рост backlog, потерь или задержки, совпадающий с CPU `d2kd`, перегрузкой
   netlink или длинным проходом по потокам. Сравнивать по монотонному времени.
2. Рост CPU `d2kc`, количества повторных проб и сетевых таймаутов при
   доступном WAN. Отдельно проверять программную пересылку после отключения
   fast NAT/flow offload. Длинный зонд сам по себе причиной не является.
3. Действия датапата на уже обменивающихся потоках во время потери туннеля.
   Агрегат требует сверки с воспроизведением на контролируемом туннеле.
4. Ошибки DNS при сохранённом IP-доступе, исчезновение маршрута/линка либо
   переполнение conntrack между минутными срезами.

Причина клиентского обрыва остаётся открытой. Изменение обработки трафика
ограничено вычитыванием ошибки NFQUEUE; правила маршрутизации, стратегии и
политика допуска измерений сохранили прежнее поведение.
