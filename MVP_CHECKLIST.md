## Поле 12-15.10 — объём, QUIC с ECH, живучесть служб

Статусы: `[x]` — доказано на проводе роутера или падающим тестом до правки;
`[~]` — правка в поле стоит, доказательство неполное. Браузер с 15.10 —
только Chrome (решение владельца); Safari из полевых прогонов убран.

- [x] Класс объёма: короткий завершённый ответ больше не считается
  отрицанием обрыва, порог берётся из обрезанного ответа, подсказки идут из
  CSS, вердикт не теряется снимком. Поле: блок около 16 КиБ разобран,
  soundcloud и tampermonkey перестали гонять перебор на работающем сайте.
- [x] QUIC: блок односторонний и измеряется по направлению. Входящие байты
  росли от повторов сервера, из-за чего обрыв записывался как пройденный
  бюджет (32 547 датаграмм читались как «обход»). `prog`/`wire`/`ack`
  разведены, заведён исход `ONEWAY`.
- [x] Межсетевой экран: обёртки `iptables`/`ip6tables` ждут блокировку
  xtables (`-w`). Без неё `iptables -C` на занятой блокировке давал rc=4
  (18 проверок из 300), сторож считал правило пропавшим, запускал `reapply`,
  тот падал так же и снимал все правила на 55 с. Тест
  `scripts/test-s99-firewall-stub.sh` (`STUB_XTABLES_BUSY`).
- [x] Обычный DNS и loopback IPC исключены из NFQUEUE на обеих платформах.
  Keenetic сохраняет точечные исключения для обычного DNS на нестандартных
  портах из `ndmc show dns-proxy`. DoH, DoT и DoQ доступны классификатору
  на OpenWrt и Keenetic, в том числе TCP/UDP 853.
- [x] `detect/raw.c`: потерянный SYN повторяется по RFC 6298 (RTO с 1 с,
  удвоение, тот же номер) вместо отказа от замера. flibusta.is эпизодами
  теряет 17-19 % SYN, и замер бросался, не дойдя до метода. Тест
  `test_lost_syn_is_retransmitted`.
- [x] HTTP: обрыв ответа без портала запускает поиск. media5.cdnbase.com
  отдавал 33 120 байт из 106 050, и ничего не искалось, потому что сигналом
  считался только ответ портала. Датапат сообщает такой обрыв кодом 4 без
  плана, поиск берёт его базовым вопросом.
- [x] Снимок QUIC — весь полёт клиента, а не одна датаграмма. Приветствие
  Chrome с ML-KEM едет двумя Initial; контроллер видел обрывок и мерил
  встроенной заготовкой. Провод v19 → v20 несёт пачку датаграмм (до 6144
  байт), зонд шлёт её по датаграммам со свежим DCID на попытку, свой клиент
  подтверждения повторяет форму клиента.
- [x] Снимок снимается, когда приветствие ЦЕЛОЕ, а не когда нашлось имя.
  Chrome переставляет расширения, и имя бывает в первой датаграмме, а
  ClientHello кончается во второй: пачка уходила из одной датаграммы и
  отвергалась как обрывок (8 обрывков за прогон, стало 1).
- [x] Контроллер падал молча на первой же пачке Chrome: рабочий поток
  копировал вход замера в стековый буфер на 2048 байт при входе 2508.
  Прогоны K, L и M этого дня не мерили ничего — панель показывала «Нет связи
  с датапатом». ASan на `test_sched`: stack-buffer-overflow, WRITE of size
  2408 в `worker_run`. Та же дыра в ячейке ECH-входа закрыта.
- [x] Ответ сервера на пачку засчитывается: проверщики брали DCID из байтов
  пачки как из одиночного Initial, разбор не проходил, и любой ответ
  отвергался — каждый замер пачкой читал «имя молчит», то есть ложную
  блокировку.
- [x] QUIC с ECH меряется пачкой клиента. Chrome ходит на цели Cloudflare с
  ECH под внешним именем `cloudflare-ech.com`; заготовка контроллера ECH не
  несёт, коробка её пропускает, и поиск кончался ложным «напрямую проходит»,
  стирая привязки имени. Датапат отдаёт ECH-пачку без заказа, контроллер
  держит пачки по именам и подтверждает план повтором пачки под планом
  (уровень рукопожатия; без ключей клиента прикладной уровень не измерим).
- [x] Доказательство QUIC-ECH привязывается к АДРЕСУ, а не к внешнему имени.
  Под одним внешним именем приходят разные цели, и один план, измеренный на
  одном адресе, раздавался всем: на проводе приманки такого плана доходили
  до сервера и получали ответ, а полёт клиента не получал ничего и умирал по
  таймеру PTO (0,3 → 0,9 → 2,1 → 4,0 с). Поле, чистый каталог: katzauction
  получил свой план на 188.114.97.1 и принял 117 КБ по QUIC, romfea 153 КБ,
  rua.gr 127 КБ, enimerosi 115 КБ; прежней картины «наружу десятки, внутрь
  ноль» нет ни на одном потоке.
- [~] QUIC в целом НЕ закрыт. Доказано: там, где Chrome идёт по QUIC, он
  проходит (4 цели из 4 на проводе). Не выяснено, почему на остальных девяти
  целях с HTTP/3 Chrome по QUIC не идёт вовсе (наружу ноль датаграмм — это
  выбор браузера, не блокировка). Прикладной успех по QUIC не измерен.
- [~] Полевой инструмент: прогон и контроль ведутся только Chrome, прогон
  сам проверяет сборку на роутере (`EXPECT`) и пишет журнал живости d2kc,
  `qwire.sh` меряет протокол по проводу для каждой цели. Прогон с умершим
  контроллером больше не выдаётся за замер. Состав целей QUIC сверен с VPS:
  HTTP/3 у 13 из 19, ECH у 10 из них.
- [ ] Прикладной успех по QUIC (полный ответ приложения под планом) не
  измерен ни на одной цели: подтверждение ECH-плана останавливается на
  уровне рукопожатия по устройству (ключей клиента у нас нет).
- [ ] Сквозная приёмка 19 целей одним прогоном с чистого каталога на этой
  сборке не проводилась: пункт 5 остаётся открытым.

  выпускаются после последней fake-посылки и FIFO; `test_udp_release` покрывает

Подробности и красные стенды: [передача 16.09](docs/field/2026-09-16-wire-and-search.md).

**Продолжение 17.09.** Незакоммиченная работа по удержанию оригиналов
зафиксирована и закрыла разрыв исполнения: стенд с цензором зелёный целиком,
включая настоящего клиента. Перенесена отмена замера, которой не было вовсе:
без неё истёкший срок ОДНОЙ задачи блокировал главный поток контроллера на всё
время её замера, и служба не выходила по сигналу. В журнал добавлены

клиента. Разбор: [передача 17.09](docs/field/2026-09-17-hold-and-cancel.md).

**Пункт 1 закрыт лабораторно 17.09.** Обе половины разрыва сошлись: датапат
удерживает оригиналы до сборки приветствия и исполняет план на составном
входе, а вертикаль доведена до клиента ЗА NAT. Оба стенда зелёные целиком.

По дороге выяснилось, что стенды с ВНЕШНЕЙ целью мерили чужую линию: трафик
уходит с машины, а на роутере автора поднят z2k, чьё правило ловит весь 443 по
порту. Один и тот же код на местной цели находит приём за 55 с и 18 зондов, на
внешней — 294 зонда за 16,8 минуты и ничего. Цель стендов переехала в своё
сетевое пространство; внешняя осталась ключом и читается с оговоркой.

**Разобрано 17.09: промах conntrack был гонкой чтения.** Запись существует,
первый запрос её не видит, повторный сразу же — видит. Цена промаха
несоразмерна редкости: попав на поток собственного зонда, он губил ВЕСЬ
найденный обход по цели («прошло 0 из 30» на рабочем плане). Промах теперь
перепроверяется тремя попытками; настоящее отсутствие записи по-прежнему
отвергает план. Разбор, числа и то, что осталось незакрытым:
[промах conntrack](docs/field/2026-09-17-conntrack-race.md).

**Пункт 4 начат и наполовину закрыт 17.09.** Вопросник QUIC доведён с одного
вопроса до семи, голосовой путь перенесён с нуля. Обе половины — лабораторно:
поля не было ни у одной. Ограничения перечислены подпунктами выше и подробно —
в двух картах переноса.

Историческое следующее действие на 17.09 — пункт 3; актуальное — в начале файла.

**Пункт 3 начат 17.09.** Зонд TLS 1.2 перенесён и работает: планировщик
